入库单创建后、出库单创建前逆向流程全集

本文参照平台导览页的表达方式整理:先看正向主链,再看逆向边界,最后把 1.1、1.2、1.3、1.4 的分支拆开。核心目标是让“货、钱、单据、状态”各自有真实承载,不靠直接改状态抹掉已经发生的事实。

项目 buildreach-fulfillment 范围:入库单创建后、出库单创建前 PR #77:1.1 已完成 PR #78:1.4 已完成 PR #80:1.3 库存/履约基础 本分支:补客户侧财务闭环

一、平台正向主链

摘自 /guide 的主链口径
报价单销售录入客户需求与成交价
→
销售单客户确认,订单成立
→
采购单按销售单向供应商订货
→
入库单供应商发货后登记在途
→
确认入库货到货代仓,产生库存
→
出库单确认出库,扣库存
→
发运柜封柜、离港、物流、报关

供应商侧钱

  • 创建入库单时,供应商应付已经成立。
  • 确认入库只产生库存,不再新产生应付。
  • 供应商接受退回/取消时,由供应商贷项单冲减应付。

客户侧钱

  • 确认出库时才产生客户应收。
  • 出库单形成前,通常还没有客户应收。
  • 客户预收/客户余额属于财务实层,不应由库存单据直接改账。

二、共同边界

单据边界

  • 创建入库单后,不能裸编辑、裸作废或裸回滚。
  • 出库单形成后,原正向履约链路终止。
  • 已经发生的事实必须由真实正向或逆向单据承载。

库存边界

  • 确认入库才产生库存。
  • 采购退货出库才扣库存。
  • 待处置库存不能混入可发库存。

财务边界

  • 供应商应付不靠状态回滚消失。
  • 客户退款不能混用采购币种。
  • 公司损失不能在货仍待处置时提前确认为最终损失。

四、1.3 供应商不接受、公司承担

这个分支不应命名为“公司承担型取消单”。公司承担只是线下业务结论,系统里应该落专业单据:库存侧是库存处置单,客户侧是客户余额/退款类财务单据,供应商侧原应付保持。

公司损失:先不最终确认

  • 库存处置只是把货转为待处置资产,不是报废事实。
  • 后续可能转售、改配、退供应商、报废或获得残值。
  • 最终损失应在最终处置方式确认后再设计,不要在库存处置创建时直接过账。
MVP 里可以记录“客户补偿/余额金额”,但不要自动等同于公司最终损失。

六、本次客户侧闭环需要落地的不变量

单据与状态

  • 客户余额贷项单有 PENDING_APPROVAL / POSTED / REJECTED / VOIDED。
  • 同一库存处置单同一时间至多一个活动贷项单。
  • 驳回必须填原因;重新提交保留 resubmitted_from_id。
  • 已过账未消耗的贷项单可作废;已抵扣的必须先反抵扣。

金额与币种

  • 金额字段使用 Decimal,不接 float。
  • 本 MVP 固定 CNY,不与 PO 币种或 SO 币种相加。
  • customer_credit_allocations 独立于 receipt_allocations,现金与余额来源可区分。
  • 贷项单与应收的 amount_allocated 必须在同一事务同步更新。

权限与并发

  • 业务侧持 customer_credit:create,财务侧持 customer_credit:post / customer_credit:void。
  • 创建人不可过账自己创建的客户余额贷项单。
  • 自动抵扣按已过账客户贷方单 created_at ASC, id ASC FIFO。
  • 重复提交、重复过账、并发创建、驳回后重试都要测试。

七、出库单形成后的边界

售后逆向不是本次范围

  • 出库单形成/确认出库后,原正向履约链路终止。
  • 不回滚原销售单、采购单、入库单、出库单。
  • 后续客户退货、退款、换货、报废、残值、转售,都应新建售后型逆向流程并关联原单据。
